# ADR: 使用回调式最小管线统一 AI 调用生命周期

- Status: Accepted
- Date: 2026-08-12
- Owner: LearningManage 开发者

## Context

LearningManage 已包含任务拆解、今日任务推荐、日报改名、清单重排和周总结润色等 AI 场景。现有 `AiServiceImpl` 约 2382 行，同时包含业务查询、Prompt 构造、模型调用、调用日志、响应解析、规则降级和草稿状态处理。

多个场景已经重复实现以下技术流程：

```text
解析提示词
→ 创建 AI 调用日志
→ 调用 AiModelClient
→ 更新实际模型和重试次数
→ 解析并校验模型响应
→ 更新调用日志终态
```

本次重构需要减少该技术流程的重复，同时保持现有 API、Redis 限流、数据库结构、场景失败行为和草稿机制不变。首个实现切片只迁移今日任务推荐顺序，以验证抽象是否成立。

## Decision

采用“回调式最小 AI 调用管线”。

公共 `AiInvocationPipeline` 负责提示词解析、调用日志生命周期、`AiModelClient` 调用、执行元数据更新以及调用响应处理回调。每个业务场景继续负责业务数据查询、用户 Prompt 构造、响应解析和业务校验规则，以及失败后报错或降级的产品决策。

响应解析通过泛型函数式接口传入管线，管线不使用场景 `switch`，也不依赖 `Task`、`Project` 等业务实体。

本阶段只迁移今日任务推荐：

- API 请求和响应保持不变。
- Redis 限流继续由现有拦截器执行。
- 模型调用或场景响应处理失败时继续使用原有规则降级。
- 调用日志采用尽力而为语义，日志故障不阻断能够正常完成的主流程。
- 管线不使用覆盖模型调用的数据库事务。
- 不修改数据库和草稿存储。

## Alternatives Considered

### Alternative 1: Handler + 注册表

- Benefits：每个 AI 场景可以形成独立组件；场景选择和执行入口统一；场景数量较多时更易扩展。
- Disadvantages：当前只迁移一个场景，尚未通过多个迁移场景验证真实变化点；会立即增加 Handler、注册表和可能的工厂类，抽象成本较高。
- Reason not selected：现阶段优先验证最小公共骨架，避免在差异尚未稳定前建立平台化结构。至少迁移三个场景并确认其输入准备、解析和降级契约稳定后再重新评估。

### Alternative 2: 抽象模板父类

- Benefits：能够用模板方法固定执行顺序，子类覆盖场景步骤。
- Disadvantages：业务场景必须进入继承层次；Spring 服务组合能力受限；可选步骤容易演变为空方法和条件分支；不同场景同时具有解析、降级、草稿等多维差异。
- Reason not selected：当前差异更适合通过组合和回调表达，继承会让公共技术流程与业务生命周期耦合。

### Alternative 3: 保持现状

- Benefits：没有短期重构成本，也没有迁移风险。
- Disadvantages：`AiServiceImpl` 会继续增长；各场景的日志终态、异常分类和调用元数据更新容易分叉；后续接入更多 AI 或 RAG 场景时重复进一步扩大。
- Reason not selected：重复已经出现在多个现有场景中，且即将继续完善 AI 接口，具备实施最小抽象的现实收益。

## Consequences

- Positive：模型调用和日志生命周期集中实现；场景仍保留业务规则和降级控制；可以逐个迁移并独立测试；不影响现有外部 API 和数据结构。
- Negative：迁移期间 `AiServiceImpl` 内会暂时同时存在旧调用辅助方法和新管线；回调式调用在场景增多后可能出现重复的命令组装代码。
- Operational：所有构建和测试必须使用项目要求的 JDK 17。2026-08-12 基线验证中，默认 JDK 8 无法运行 Java 17 编译的测试；使用 `JAVA_HOME=D:\JDK17` 后 24 个测试全部通过。

## Risks

- Authorization and data isolation：公共管线不负责授权；业务场景必须在进入管线前完成用户身份和数据归属过滤。今日排序响应校验必须拒绝输入集合之外的 taskId。
- Transaction and idempotency：外部模型调用不得进入长事务。今日推荐没有正式业务写入，本阶段不增加幂等键；每次调用单独记录日志。
- Timeout and retry：超时和兜底模型继续由现有 `AiModelClient` 管理。管线只记录实际执行结果，不额外增加重试，避免重复费用和重试语义冲突。
- Model or Tool uncertainty：HTTP 成功不等于业务成功；只有场景解析和业务校验通过后才能将调用日志标记为成功。
- Testability and observability：必须分别测试调用失败和响应处理失败；日志写入采用尽力而为可能造成少量日志缺失，因此应用警告日志仍需保留。

## Future Triggers for Reconsideration

出现以下任一条件时重新评估 Handler + 注册表或更完整的 AI 执行框架：

1. 至少三个 AI 场景完成管线迁移，并表现出稳定、重复的场景准备和结果处理契约。
2. `AiServiceImpl` 在迁移后仍因场景命令组装产生明显重复。
3. 需要从 HTTP 之外的定时任务、内部服务或消息消费者统一调用 AI 场景。
4. 不同场景需要可配置的重试、降级、成本预算或超时策略。
5. 接入 RAG 后需要统一编排多种上下文提供器，但仍应另行进行设计评审。
6. 模型调用转为异步任务，出现持久化执行状态、取消、恢复或工作流编排需求。
