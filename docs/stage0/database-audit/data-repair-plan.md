# 数据修复方案草案

状态：2026-08-17 已完成恢复库演练，并经用户确认后完成主库逻辑删除；主库执行记录见 `main-repair-execution-2026-08-17.md`。

## 1. 目标

在不破坏原始数据的前提下，使活跃业务数据满足基本关联完整性：

```text
活跃项目必须有有效用户
活跃任务必须有有效项目
活跃里程碑必须有有效项目
团队成员必须有有效用户和团队
```

## 2. 修复顺序

```text
主库重新备份
→ 在隔离恢复库执行候选修复
→ 重新执行只读审计
→ 执行 API 和后端测试
→ 验证回滚
→ 评审修复 SQL
→ 维护窗口修改主库
→ 主库复核
```

## 3. 推荐处理策略

### 孤儿项目

优先恢复缺失用户；只有在确认项目属于无效数据且无法恢复用户时，才考虑逻辑删除。

禁止：

- 随机指定一个现有用户。
- 创建虚假用户补齐关联。
- 直接物理删除项目。

### 孤儿任务

优先从备份恢复原项目；如果无法恢复，需要业务确认任务是否保留。当前数据库没有“待归属项目”状态，因此不能把任务随意挂到新建项目。

禁止：

- 根据任务标题猜测项目。
- 根据创建用户自动创建项目。
- 直接删除任务正文。

## 4. SQL 执行要求

后续修复 SQL 必须满足：

- 使用事务。
- 使用主键和旧值作为前置条件。
- 执行前输出目标记录数量。
- 执行后检查影响行数。
- 影响行数不符合预期时回滚。
- 不执行无条件批量更新。
- 不使用物理 `DELETE`。
- 保存修复前后摘要和操作人。

## 5. 自动化门禁

后续 Flyway 和 Testcontainers 测试中增加：

- `project.user_id` 关联完整性。
- `task.project_id` 关联完整性。
- `milestone.project_id` 关联完整性。
- `team_member` 双向关联完整性。
- 固定角色和状态枚举检查。
- 逻辑删除数据不参与活跃关联检查。

## 6. 主库执行门槛

在以下条件满足前，不修改主库：

- RBAC 表所有权已经确认。
- DQ-001 有明确处理决定。
- DQ-002 有明确处理决定。
- 隔离库修复和回滚均验证通过。
- 修复 SQL 经人工审阅。
- 已生成新的主库备份。

## 7. 演练脚本

- `sql/repair/stage0/01_apply_orphan_logical_delete.sql`：恢复库逻辑删除，包含数据库、候选数量和影响行数保护。
- `sql/repair/stage0/02_verify_orphan_logical_delete.sql`：修复后关联完整性、目标状态和稳定规则验证。
- `sql/repair/stage0/03_rollback_orphan_logical_delete.sql`：根据同一修复时间标记恢复旧值，并校验影响行数。
