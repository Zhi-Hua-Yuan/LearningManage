# LearningManage 项目介绍稿

## 使用说明

- 1 分钟版用于自我介绍、简历项目追问的第一轮回答。
- 3 分钟版用于面试官说“详细介绍一下项目”时使用。
- 10 分钟版用于项目答辩、技术面深挖或配合系统演示。
- 口述时不需要逐字背诵，但数字、状态和技术边界不要随意扩大。

---

## 1 分钟版

我做的项目叫 LearningManage，它不是一个简单接入大模型的聊天 Demo，而是一个 AI 原生的项目与学习管理系统。

用户可以输入目标，让 AI 生成项目、里程碑和任务草稿，确认后进入正式任务协作。任务和周复盘会通过 Transactional Outbox 异步建立向量索引，之后用户可以在项目范围内做 RAG 问答，系统返回可验证的 `[S1]` 引用。项目风险和团队负载则由异步 Agent 调用白名单中的只读 Tool 分析，最后仍然只生成草稿，由用户确认后保存报告。

这个项目我重点解决了三个问题：第一，用统一 `PermissionService` 做多用户和团队权限隔离；第二，以 MySQL 为事实源，通过租约、Fence Token 和内容哈希保证 Qdrant 最终一致；第三，限制 Agent 只能使用强类型、二次鉴权的只读工具，不能直接修改业务数据。

工程上还包含 Flyway、前后端契约测试、AI 评测、Token 和成本记录、Prometheus、Grafana、Tempo，以及依赖故障降级。它展示的是一条完整、可测试、可审计的 AI 应用后端链路。

## 3 分钟版

### 0:00～0:35：项目定位

我做的项目叫 LearningManage，是一个 AI 原生的项目与学习管理系统。它最开始已经有项目、里程碑、任务、团队、周复盘和 AI 任务拆解，我后续升级的重点不是继续堆 AI 按钮，而是把它做成一个具备权限、一致性、评测和运维能力的完整 AI 应用。

核心用户链路是：用户输入目标，AI 先生成任务拆解草稿；用户确认后创建项目、里程碑和任务；团队成员被分配任务并持续更新，周复盘形成历史；RAG 基于这些历史回答问题并返回引用；Agent 再结合任务统计和历史证据分析项目风险或团队负载，结果仍以草稿形式交给用户确认。

### 0:35～1:15：业务和权限

系统首先把业务语义补完整了。任务同时记录创建人和受理人，任务转派有审计日志，成员退出时会在事务内解除未完成任务。周复盘分 PRIVATE 和 TEAM，私人反思永远只有作者能看，团队侧只能看到单独填写的共享摘要。

所有权限统一进入 `PermissionService`。权限不是相信前端传来的角色，而是根据登录用户、项目归属、有效团队成员关系和资源当前状态计算。平台 `SYSTEM_ADMIN` 只拥有运维权限，不会自动获得私人业务数据。批量列表和 AI 场景使用批量鉴权，避免 N+1 查询。

### 1:15～1:55：AI 管线和 RAG

所有模型请求经过统一的 `AiInvocationPipeline`。它负责 Prompt 版本、Trace、调用日志、Usage、Token、估算成本、超时、熔断和主备模型回退；业务服务负责权限、结果解析和确定性降级。敏感内容在发送供应商前会经过清洗，RAG 和 Agent 默认只记录元数据，不保存问题、证据和答案正文。

知识索引使用 MySQL Transactional Outbox。业务数据和索引事件在同一事务提交，Worker 再读取 MySQL 当前状态，进行规范化、切片和哈希比较，然后幂等写入 Qdrant。事件只是唤醒信号，不是事实快照；即使事件乱序，最终也以 MySQL 当前状态为准。

RAG 查询有三次权限检查：供应商调用前检查项目，召回后批量检查来源并从 MySQL 重建正文，回答保存前再次检查权限和内容哈希。模型只看到服务端分配的 `S1` 到 `S8`，不能自行构造业务 ID；引用集合和正文标记不一致时只允许修复一次。

### 1:55～2:35：Agent

Agent 采用持久化异步 Run，状态包括 PENDING、RUNNING、SUCCEEDED、PARTIAL、FAILED、TIMED_OUT 和 CANCELED。Worker 使用租约、心跳和 execution token，旧 Worker 失去租约后不能覆盖新结果。

项目风险支持 Qwen Tool Calling，允许调用任务统计、逾期任务和项目历史等白名单只读 Tool。每个 Tool 都有强类型参数、场景白名单、次数限制，并在内部再次鉴权。团队负载采用固定工作流，而且管理版与公开版使用两条隔离 Prompt；普通成员只能看到公开摘要和自己的指标。Agent 永远不能直接写项目或任务，只能生成草稿。

### 2:35～3:00：工程证据与总结

工程方面，数据库通过 Flyway V1 到 V8 前向迁移，前后端有运行时 OpenAPI 契约门禁。阶段 5 的 RAG 完成了 50 个应用路径检索与引用用例，阶段 6 的 Agent 确定性评测是 100 个用例全部通过。阶段 7 本地验证还覆盖了 MySQL、Redis、Qdrant 和可观测组件故障，证明 AI 依赖异常不会拖垮核心项目管理功能。

所以这个项目最有价值的部分，不是“用了大模型”，而是把权限感知 RAG、可恢复 Agent、人工确认写入和生产治理组合成了一条可解释、可测试、可审计的完整链路。

## 10 分钟版

### 0:00～0:50：为什么做这个项目

我介绍的项目叫 LearningManage，是一个 AI 原生的项目与学习管理系统。

很多 AI 项目的典型做法，是在现有 CRUD 系统旁边增加一个聊天框：把用户输入拼到 Prompt 里，再把模型输出展示出来。这种方案演示很快，但进入真实多用户系统后，会立即遇到几个问题：模型能看到哪些数据、向量索引如何与业务数据保持一致、模型返回的引用是否真实、Agent 能不能越权调用工具、模型失败会不会影响核心业务，以及如何证明 Prompt 更新没有让质量下降。

LearningManage 的目标就是围绕这些问题，做一条完整的 AI 应用工程链路，而不是只展示模型效果。

### 0:50～1:45：业务闭环

系统的基础业务包括用户、团队、项目、里程碑、任务和周复盘。

用户输入一个目标后，AI 会生成项目、里程碑和任务结构，但不会直接落正式表，而是先创建草稿。用户检查后确认，系统才在事务中创建正式业务数据；取消、过期或者重复确认都不会产生新的数据。

进入协作阶段以后，任务会同时记录创建人和受理人。OWNER 或 ADMIN 可以分配和转派任务，成员可以推进分配给自己的任务。每次分配都有审计记录，成员退出或被移除时，系统会锁定成员关系和相关任务，在同一个事务中解除未完成任务的受理人，并记录退出或移除原因。

周复盘不是简单的一段公开文本。它分为 PRIVATE 和 TEAM：反思和下周计划始终属于作者私人数据；如果要向团队共享，用户必须单独填写 `sharedSummary`。这样后面的 RAG 和 Agent 可以使用团队摘要，但不会因为共享复盘而泄漏私人反思。

### 1:45～2:40：权限模型

权限层是后续所有 AI 能力的地基。

系统有平台角色和团队角色两套边界。平台角色是 USER 和 SYSTEM_ADMIN，团队角色是 OWNER、ADMIN 和 MEMBER。SYSTEM_ADMIN 可以查看脱敏运维指标、重放 DEAD 索引事件或执行受控数据清理，但不能因为是平台管理员就读取用户私人项目和复盘。

业务权限统一由 `PermissionService` 根据服务端事实计算。比如项目属于个人还是团队、当前用户是否是有效成员、任务受理人是谁、复盘是否共享。前端传来的角色、团队 ID 和 capability 都不能作为授权依据。

对于批量任务、RAG 候选和报告来源，系统提供批量鉴权接口，避免在循环中逐条查询数据库。AI 草稿确认时也会重新鉴权，因为预览时有权限不代表确认时仍然有权限。

### 2:40～3:40：统一 AI 调用管线

在模型调用层，所有场景都经过 `AiInvocationPipeline`。

场景服务先准备经过权限验证的最小业务上下文，然后通过 Prompt Code 获取固定版本的 System Prompt。Pipeline 创建 RUNNING 日志，再调用 `AiModelClient.chat`。ModelClient 负责 OpenAI 兼容协议、Tool Calling 消息、主备模型、超时和上游响应解析。

内容发送给供应商前会经过 `AiContentSanitizer`。高置信度的 JWT、API Key 或密码会被替换，无法安全处理时直接阻止调用。模型调用具有全局并发舱壁和按实际模型隔离的熔断器。主模型失败且属于网络、超时、429、5xx 或协议异常时，最多切换一次兜底模型；认证和参数错误不会盲目重试。

Pipeline 会记录实际模型、供应商请求 ID、Usage、Token、价格版本、估算成本、回退和规则降级。Usage 或价格不完整时成本保持未知，而不是写成 0。RAG 和 Agent 使用 metadata-only 日志，避免问题、证据、Tool 结果和答案进入通用调用日志。

### 3:40～5:05：Outbox 和知识索引一致性

任务或复盘变化以后，不能在业务事务里同步调用 Embedding 和 Qdrant，否则外部依赖超时会拖垮正式业务。因此系统使用 Transactional Outbox。

业务 Service 在写 MySQL 数据的同一个事务中插入索引事件。事务提交后，Knowledge Worker 使用 `SELECT FOR UPDATE SKIP LOCKED` 领取事件，并写入 claim token 和租约。为了避免多个 Worker 同时处理同一个来源，它还要获取 source-level lock。

一个重要设计是：事件不是数据快照，只表示“这个来源需要重新对账”。Worker 每次都重新读取 MySQL 当前状态，根据任务或复盘生成期望文档。文本经过 `norm-v1` 规范化，再按最大 1,200 字符、150 字符重叠的 `chunk-v1` 切片。

系统分别计算 `contentHash` 和 `payloadHash`。正文变化时重新生成 Embedding；只有状态、截止日、受理人或权限 Payload 变化时，只覆盖 Qdrant Payload，不重复支付 Embedding 成本；都没变化时不执行外部写入。Point ID 由 documentKey 和 chunkIndex 确定，所以重复执行仍然是覆盖写入。

外部写入后，Worker 会再次读取 MySQL。如果处理期间正文或权限变化，就插入纠正事件。所有进度和终态更新都带当前 token，旧 Worker 即使在租约失效后恢复，也不能覆盖新 Worker 的状态。

### 5:05～6:20：RAG 检索和证据引用

RAG 提供单项目、单轮问答。它不是直接从 Qdrant 取出文本交给模型，而是一个三次鉴权流程。

第一次，在生成查询向量前校验用户能否查看项目。第二次，Qdrant 根据 project、visibility、owner 或 team 做过滤召回 Top 20 后，应用批量检查每个任务和复盘的当前权限，并根据 ID 从 MySQL 重新生成当前正文。Qdrant Payload 只用于定位候选，不是可信业务事实。内容哈希不一致的候选会被丢弃并触发纠正事件。

通过检查的候选使用 `qwen3-rerank` 重排，最多保留 8 条。服务端给证据分配 S1 到 S8 的临时编号，并明确告诉模型这些正文是不可信资料。模型必须返回 answer、insufficientEvidence 和 citations；答案中的 `[S1]` 标记必须与 citations 集合完全一致。模型不知道真实业务 ID，因此无法伪造引用关系。

如果没有授权证据，系统不会调用 Chat，而是确定性返回“依据不足”。模型生成后，系统还会进行第三次权限和哈希检查，防止生成期间用户退出团队或者来源被删除。历史结果每次读取也会重新验证，内容更新后是 STALE，删除或失权后是 INVALIDATED，过期后不再返回正文。

### 6:20～7:50：受控异步 Agent

Agent 不是同步接口。用户提交项目风险或团队负载分析时，系统先鉴权，再通过 user、scene 和 clientRequestId 幂等创建 PENDING Run，并立即返回 runId。

Worker 使用租约、心跳和 execution token 领取任务。运行状态包括 PENDING、RUNNING、SUCCEEDED、PARTIAL、FAILED、TIMED_OUT 和 CANCELED。运行中的取消是协作式的：当前只读操作结束后停止。旧 Worker 的 token 失效后，不能再写进度、草稿或终态。

项目风险支持真实 Qwen Tool Calling，允许的工具包括任务列表、逾期任务、任务统计和项目历史。工具策略按场景维护白名单，同一个工具不能重复调用，总次数最多 4。模型提供的参数先通过强类型 DTO 校验，而且 projectId 和 teamId 由 Run 固定，不能让模型改变目标。每个 Tool 内部还会再次调用 PermissionService，并且所有 Tool 都是只读的。

模型不支持 Tool Calling或者调用过程失败时，可以降级到固定工作流；历史检索失败时，也可以只使用结构化任务统计生成 PARTIAL 结果。Agent 会记录开始和结束数据版本，数据变化时不允许把旧分析伪装成稳定结论。

团队负载使用固定工作流。管理版可以使用成员级事实，公开版只接收后端生成的匿名聚合数据，两者使用独立 Prompt。普通成员读取报告时，只能看到公开摘要和自己的指标。

无论哪种 Agent，终点都只是草稿。用户确认时，系统重新检查 Run 所有权、当前资源权限、数据版本和引用哈希，然后通过草稿 Handler 幂等创建正式报告。Agent 没有任何直接修改项目和任务的工具。

### 7:50～8:45：可观测性与故障隔离

系统通过 Micrometer 暴露低基数指标，Prometheus 负责采集，Grafana 提供六个仪表盘和十条告警规则，Tempo 保存 OpenTelemetry Trace。指标标签不使用用户 ID、项目 ID、Run ID 或 Trace ID，避免高基数问题和身份泄漏。

健康检查分成公共兼容健康、Liveness、Core Readiness 和 AI Dependencies。MySQL 故障会让核心 Readiness 失败；Redis、Qdrant、模型、Prometheus 或 Tempo 故障只会让 AI 依赖降级，不会让项目和任务 API 被错误摘除。

数据生命周期通过持久化 Cleanup Run 和 Item 执行，正式清理前必须绑定一次成功 Dry Run。运行中的 AI、RAG、Agent 记录和 DEAD 索引事件不会被自动删除；正式报告一直保留到用户主动删除。

### 8:45～9:35：验证证据

项目数据库已经从 Flyway V1 演进到 V8，并同时验证空库安装和存量升级。阶段 5 的后端 CI 通过了 801 个确定性测试，RAG 应用路径评测是 50 个用例全部通过，同时完成了真实 Embedding、Rerank、Qdrant 和 Qwen 引用回答的受保护验证。

阶段 6 的 Agent 确定性应用路径评测包含 100 个用例，其中项目风险 30 个、团队负载 30 个、未注册 Tool 注入 20 个、非法参数与受控失败 20 个，结果全部通过，而且没有创建任何正式报告。

阶段 7 本地验收中，后端三个验证分区分别通过 803、61 和 5 个测试，前端通过 502 个测试；Docker 环境启动了 MySQL、Redis、Qdrant、后端、Prometheus、Grafana 和 Tempo，并完成 MySQL、Redis、Qdrant 与可观测组件故障演练。

这里我会明确区分确定性 Stub、真实供应商冒烟和最终语义质量。阶段 7 已正式发布，但其中受保护的真实 Qwen 可观测性验证由用户显式豁免，不能写成通过；阶段 3 的完整真实模型盲测与人工复核仍属于最终验收待办。

### 9:35～10:00：总结

这个项目最终形成了三条核心技术主线：第一，统一权限和人工确认保证 AI 不越过业务边界；第二，Transactional Outbox、当前状态重建和 Fence Token 保证索引最终一致；第三，证据化 RAG 和只读 Agent 保证模型结论可引用、工具执行可控制。

所以 LearningManage 展示的不只是 Spring Boot 接入大模型，而是一个 AI 功能如何在多用户业务系统中被安全地调用、持久化、评测、监控和降级。我认为它最能体现的是 AI 应用后端的系统设计和工程落地能力。
