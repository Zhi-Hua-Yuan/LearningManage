# 阶段 1 需求合同：业务语义与统一权限

状态：`FROZEN`

合同版本：1

建立日期：2026-08-23

## 1. 问题定义

当前实现主要使用资源表中的 `user_id` 判断访问权。该方式可以支撑个人项目，但不能同时表达团队项目中的创建人、受理人和管理者，也不能支撑周复盘的私人正文与团队摘要隔离。

已确认的现状包括：

- `task.user_id` 同时承担归属和权限过滤语义；
- V1 已存在未被 Java 映射的 `task.assignee_id`；
- `weekly_review` 没有稳定项目/任务关联、可见范围或共享目标；
- 项目、任务、团队、统计和 AI 服务分别实现权限判断；
- `user.user_role` 仍使用 `user/admin` 小写值，V1 租户 RBAC 表尚无应用调用方；
- 团队模块没有主动退出、移除成员和退出后解除任务分配的完整链路。

## 2. 术语

| 术语 | 固定含义 |
|---|---|
| 创建人 | 创建任务的用户；阶段 1 不因转派而变化 |
| 受理人 | 当前负责执行任务的用户；可以为空 |
| 分配人 | 最近一次改变受理人的操作人 |
| 系统角色 | `USER` 或 `SYSTEM_ADMIN`，来源为 `user.user_role` |
| 团队角色 | `OWNER`、`ADMIN`、`MEMBER`，来源为有效 `team_member` |
| 个人项目 | `project.team_id IS NULL`，只允许项目所有者访问 |
| 团队项目 | `project.team_id IS NOT NULL`，访问范围由当前团队成员关系决定 |
| 私人正文 | 周复盘的 `reflection`、`nextPlan` 及作者完整关联信息 |
| 共享摘要 | 作者显式填写、允许指定团队读取的 `sharedSummary` |
| 有效成员 | `team_member.is_delete=0` 且所属团队有效 |

## 3. 功能需求

### S1-F-001 任务身份语义

- `task.user_id` 的业务语义固定为创建人。
- Java 实体和外部 VO 使用 `createdByUserId` 命名，不继续暴露模糊的 `userId`。
- 当前受理人使用唯一字段 `assignee_user_id`。
- 创建人不会因为分配、转派、退出团队或任务完成而变化。

### S1-F-002 任务初始分配

- 个人项目创建任务时，受理人默认为项目所有者；显式受理人只能是项目所有者。
- 团队项目创建任务时，受理人可以为空；若指定，必须是当前有效团队成员。
- TEAM `MEMBER` 不具备创建或分配任务的管理权限；`OWNER`、`ADMIN` 具备。
- 存量任务按 V2 数据字典完成确定性回填。

### S1-F-003 分配、转派和解除

- 分配操作使用独立接口，不通过普通任务更新接口修改受理人。
- 只有个人项目所有者或团队 `OWNER`、`ADMIN` 可以改变受理人。
- 请求携带 `expectedAssigneeUserId`，服务端使用行锁或 CAS 阻止并发覆盖。
- 实际受理人没有变化时返回成功但不重复写历史。
- 每次实际变化与一条不可变分配日志处于同一事务。

### S1-F-004 成员退出和移除

- `MEMBER`、`ADMIN` 可以主动退出团队；`OWNER` 在阶段 1 不允许直接退出。
- `OWNER` 可以移除 `ADMIN` 或 `MEMBER`；`ADMIN` 只能移除 `MEMBER`。
- 成员关系失效前，将其在该团队项目中的未完成任务解除分配。
- 状态为 `0` 的任务视为未完成；状态 `1/2/3` 保留历史受理人。
- 解除分配、写历史和失效成员关系必须原子提交。
- 用户重新加入团队时不自动恢复历史任务。

### S1-F-005 成员任务权限

- 团队成员均可查看有效团队项目和任务。
- `OWNER`、`ADMIN` 可修改任务内容、调整优先级/里程碑、更新状态、分配和删除。
- 作为受理人的 `MEMBER` 可修改标题、描述、截止日期并更新状态。
- `MEMBER` 不可修改优先级、里程碑、受理人，不可删除任务。
- 非受理 `MEMBER` 对任务只读。
- 具体矩阵以 [权限矩阵](../authorization/permission-matrix.md) 为准。

### S1-F-006 周复盘隐私

- 新建和存量周复盘默认 `PRIVATE`。
- 作者始终可以读取自己的完整复盘。
- `PRIVATE` 复盘除作者外无人可读，包括团队 `OWNER`、`ADMIN` 和 `SYSTEM_ADMIN`。
- `TEAM` 复盘首版只允许指定一个团队，并要求单独填写非空共享摘要。
- 指定团队的当前有效成员只能读取共享 VO；共享 VO 不定义 `reflection` 和 `nextPlan` 字段。
- 团队角色不能扩大私人正文读取范围。

### S1-F-007 周复盘关联

- 周复盘可以关联一个稳定的重点项目和多个任务。
- 保存时批量校验所有关联资源的访问权。
- TEAM 复盘的重点项目和关联任务必须属于指定团队。
- PRIVATE 复盘可以关联作者可访问的个人或团队资源。
- 读取关联资源时重新校验当前权限，不能只依赖保存时的结果。

### S1-F-008 周统计口径

- `completedTaskCount` 按 `assignee_user_id` 和完成时间统计，表示用户实际完成的任务。
- `focusProject` 基于用户实际完成的受理任务计算。
- 创建人维度和受理人维度不得在统计或 AI 查询中混用。

### S1-F-009 系统角色

- `user.user_role` 值规范为 `USER`、`SYSTEM_ADMIN`。
- 注册用户默认 `USER`。
- 未知存量角色阻断迁移预检，不静默归类。
- `SYSTEM_ADMIN` 只提供明确列出的平台运维权限，不自动绕过项目、任务或私人复盘权限。
- V1 租户 RBAC 五表在阶段 1 保持未启用状态。

### S1-F-010 统一权限入口

- 项目、里程碑、任务、团队、周复盘、统计和现有 AI 资源读取统一使用 `PermissionService`。
- Controller 不承担权威权限判断。
- 前端隐藏/禁用按钮不是安全边界。
- 列表、统计和 AI 批量 ID 场景必须使用批量权限方法。
- 权限拒绝使用稳定业务码 `40300`；未登录继续使用 `40100`。

### S1-F-011 API 能力提示

- 任务等需要条件操作的 VO 返回 `capabilities`。
- 前端按 `capabilities` 渲染操作，不复制完整角色矩阵。
- 后端仍对每次写操作重新鉴权，不能信任前端能力值。

### S1-F-012 现有 AI 入口

- 今日排序、清单重排、周复盘润色及草稿确认中的业务 ID 必须经过统一权限校验。
- 请求中混入不存在或越权 ID 时整体拒绝，不允许部分静默放行后继续调用模型。
- 阶段 1 不改变模型协议、Prompt 管理或降级管线。

## 4. 非功能需求

| ID | 要求 |
|---|---|
| S1-NF-001 | 越权访问放行数为 0 |
| S1-NF-002 | 私人复盘正文越权返回数为 0 |
| S1-NF-003 | 非法受理人落库数为 0 |
| S1-NF-004 | 100 个资源的列表权限检查不得产生逐资源 N+1 |
| S1-NF-005 | 分配、退出和移除流程满足事务原子性与并发保护 |
| S1-NF-006 | 日志不记录私人正文、有效凭据或完整请求体 |
| S1-NF-007 | V2 可从空库安装，也可从正式 V1 状态升级 |
| S1-NF-008 | 已发布 V1 文件保持字节级不可变 |
| S1-NF-009 | 原前端 37 个 operation 缺失数为 0；新增 operation 全匹配 |
| S1-NF-010 | 个人项目、任务、周复盘和现有 AI 拆解核心路径无回归 |

## 5. 非目标

- 不启用租户 RBAC 五表；
- 不实现 OWNER 转让；
- 不支持一份周复盘同时向多个团队发布不同摘要；
- 不增加 Qdrant、Embedding、RAG、Agent 或 Redis 权限缓存；
- 不重构所有旧 REST 路径或统一 HTTP 状态码；
- 不在 PR1 执行数据库迁移或修改生产数据。
