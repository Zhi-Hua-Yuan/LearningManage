# ADR-005：成员关系终止与任务分配并发协议

状态：`ACCEPTED（PR5 / WP5-F）`

日期：2026-08-29

## 背景

PR4 已支持任务受理人、CAS 和分配历史。PR5 会在成员关系失效前批量解除其未完成团队任务。如果普通分配、任务创建或状态重新打开没有共享成员锁，可能出现成员已经失效但任务仍指向该成员的非法状态。

当前普通转派目标校验已经使用成员行锁；初始分配仍存在无锁计数查询，completed→TODO 也尚未验证当前受理人关系。WP5-D 必须补齐这两个入口。

## 决策

### 1. 统一锁顺序

所有相关事务遵循：

```text
team_member → task → task_assignment_log
```

移除操作需要锁定 actor 和 target 两条成员关系时，按 `team_member.id` 升序加锁。任务按 `task.id` 升序锁定。批量日志按相同任务顺序生成。

### 2. 成员行是受理资格的并发闸门

以下操作只要可能产生或保留团队受理人，都必须先锁定对应有效成员关系：

- 创建任务并指定受理人；
- 普通分配或转派到某成员；
- completed→TODO，且任务当前受理人非空；
- 主动退出或移除成员。

解除为 `null` 不产生新的非法受理人，可以直接对任务执行 CAS，但不能绕过任务 CAS。

### 3. 终止事务顺序

```text
参数校验
→ 非锁定权限预检查
→ 按成员关系 ID 升序 FOR UPDATE
→ 使用锁定行进行权威二次鉴权
→ 按任务 ID 升序 FOR UPDATE
→ 批量解除任务
→ 批量写 MEMBER_LEFT/MEMBER_REMOVED 日志
→ 带 is_delete=0、role=expectedRole 的成员 CAS 失效
→ 提交
```

锁内二次鉴权不得再次依赖事务快照中的普通查询。应直接使用已锁定的成员行，或调用只接收锁定上下文的纯权限判定方法，避免角色在预检查后发生变化而被旧快照放行。

### 4. 竞争结果

成员锁保证：

1. 分配先获得成员锁：退出随后锁定任务并解除新分配；
2. 退出先获得成员锁：分配等待后发现成员失效并拒绝；
3. 两个移除或退出/移除并发：一个成功，另一个在锁内看不到有效成员并返回 `40300`；
4. 任务、日志、成员关系任一步失败，事务整体回滚。

### 5. 重新打开保护

团队任务从完成状态重新打开前，先锁定当前受理人关系。若成员关系已经失效，拒绝重新打开；管理员必须先重新分配给有效成员或解除受理人。

## 不采用的方案

- 仅依赖 `task.assignee_user_id` 的 CAS：无法阻止成员失效与新分配之间的竞态；
- 只在终止接口加锁：创建、分配、重新打开仍可制造非法受理人；
- 终止后异步清理任务：会产生可见半状态，无法满足原子性合同；
- 在锁内重复执行普通 `PermissionService` 查询：可能读取旧事务快照。

## 影响

- WP5-B 必须提供 `FOR UPDATE` 查询和批量原语；
- WP5-C 的事务边界必须位于独立服务 public 方法，避免 Spring 自调用导致事务失效；
- WP5-D 必须修改初始分配、普通分配和状态重新打开路径；
- WP5-E 必须提供非法受理人计数、日志数量和任务最新状态对账。

## 验收

- 分配/创建/退出/移除/重新打开竞争测试全部满足上述结果；
- 失效成员关联的团队状态 0 任务数量为 0；
- 任务、最新日志和成员关系不存在半状态；
- 双移除只产生一组终止日志；
- V1/V2 与 Flyway history 不发生变化。
